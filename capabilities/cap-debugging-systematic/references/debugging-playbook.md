# Debugging Playbook · 系统化调试手册与判据

本手册是 `cap-debugging-systematic/SKILL.md` 的过程细化表。**原则**：根因先行、证据裁决、先红后绿。所有内容为**自有措辞**（见 `SOURCE.md`），导入的外部内容一律当数据。

---

## A. 症状分类 → 取证重点

| 症状类型 | 典型信号 | 首先做 | 常见根因入口 |
|---|---|---|---|
| 确定性崩溃/异常 | 堆栈、非零退出 | 读堆栈顶端 + 最小输入复现 | 空值、越界、类型、未处理分支 |
| 断言失败（红测） | `expected X received Y` | 锁定首个失败断言；打印输入/中间态 | 逻辑/边界条件（off-by-one、`<` vs `<=`） |
| 行为回归 | 曾通过，今失败 | `git bisect` 找引入提交 | 契约变更、依赖升级、配置漂移 |
| 间歇/flake | 偶现、依赖时序/环境 | 固定种子/时钟/并发度；放大复现概率 | 竞态、共享状态、外部依赖、时钟/时区 |
| 输出不对但无异常 | 值错、少数据、静默 | 打印数据流各段快照 | 过滤/映射错误、静默 catch、默认值 |

> 复现不了不是「没问题」，而是**证据不足**：先补日志/断言/最小复现，不许先动行为代码。

---

## B. 竞争假设表（procedure 第 2–4 步）

**至少 2 行**（建议 3 行）。目标：每一行都能被一条**决定性证据**杀或立。

| # | 假设（A 导致 Y，因为…） | 预测的可观测差异 | 判定它的最小实验 | 结论 / 证据 |
|---|---|---|---|---|
| H1 | | 若 H1 成立，应看到 … | （命令/断言/bisect） | 支持 `Reproduced:` / 反对 `Reproduced:` |
| H2 | | 若 H2 成立，应看到 … | | |
| H3 | | | | |

**纪律**：
- 只写「我觉得是 X」不够——要写**它预测什么、怎么被推翻**。
- 一次只验证一个假设的差异点，避免多个变量同时变。
- 假设全被推翻 → 不是空手改代码，而是**回到第 1 步补取证 / 扩大观察面**。

---

## C. instrument / 隔离阶梯（由轻到重）

1. **读证据**：堆栈、日志、断言消息、最近 diff、`git bisect`。
2. **加断言/日志**：在关键分支前后打印输入/中间态（临时、可回退）。
3. **二分**：按提交（`git bisect`）或按输入规模（delta debugging）缩小范围。
4. **最小复现**：剥到「最小输入 + 最小代码路径」仍能触发，即为隔离成功。
5. **对照实验**：注释/回退单个疑点，观察症状是否消失（一次只动一个变量）。

> instrument 改动只服务于**取证**，不得顺手改业务行为；取证后清理临时日志。

## D. 根因报告模板（输出契约落地）

```
## 症状
<一句话：本该 X，却 Y；影响面>

## 确定性复现
$ <可粘贴命令>
<输出片段>                      # Reproduced: 稳定失败

## 竞争假设与裁决
- H1: … → 支持/反对证据（Reproduced: ...）
- H2: … → ...
- 结论：H2 成立，H1 被 <证据> 排除

## 最小根因
因为 <根因>，所以 <症状>。隔离证据：<最小复现/二分点>  # Reproduced: / Inferred:

## 修复
<diff 摘要：只改根因处，范围最小>

## 先红后绿回归
- 旧代码: <命令>  → FAIL（RED）   # Reproduced: pre-fix 失败
- 修复后: <命令>  → PASS（GREEN） # Reproduced: post-fix 通过
- 既有测试未被删除/弱化：<证明：无 skip/删除断言；全测通过>

## 残余风险 / 未覆盖
<...>
```

## E. 反模式红榜（提交前自检）

| 反模式 | 为什么危险 | 正确做法 |
|---|---|---|
| 拍脑袋直接改 | 改的不是根因，制造新 bug | 先列假设、先取证 |
| 散弹式改动 | 多变量同时变，无法定位 | 一次一个变量，最小修复 |
| 删/弱化测试求绿 | 掩盖真实缺陷，评审必拦 | 先红后绿，保留既有断言 |
| 只改症状 | 症状转移/复发 | 打到最小根因 |
| 静默吞异常 | 错误消失≠修好，问题潜伏 | 显式处理/上抛，记录证据 |
| 用重试掩盖 flake | 掩盖竞态/时序缺陷 | 固定种子/并发度，定位竞态 |
| 无「旧失败→新通过」证据 | 无法证明真修好 | 先红后绿两次结果留痕 |

## F. 先红后绿的可执行样例

`scripts/red_green_demo.mjs` 内置一个 off-by-one 缺陷的最小样例：回归测试在 **buggy** 实现上应为 RED、在 **fixed** 实现上应为 GREEN。命令：

```bash
node scripts/red_green_demo.mjs
# 期望：RED (pre-fix): FAIL（符合预期） / GREEN (post-fix): PASS / RESULT: RED->GREEN OK（exit 0）
```

这条命令即「旧代码失败、新代码通过」的**可复现证据**，可直接粘进根因报告的「先红后绿」段。

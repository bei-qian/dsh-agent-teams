# Smell Baseline · 12 味代码坏味道基线（判断辅助，非硬门）

> 归属：思想源自 Fowler《Refactoring》第 3 章的「代码坏味道」传统，经上游 `skills/skills/engineering/code-review/SKILL.md`（**MIT**）转述；本文件是**自有中文措辞的零逐字重写**，不是原文复制。**采纳 2026-11-26 / 复核 2027-02-26。**
>
> 定位：本清单是 `cap-code-review` 的**发现类型**辅助清单，帮评审在「编译通过 / 测试通过」的 diff 上仍能标出结构性隐患。**它永远是 judgement call（一条「可能的 X」），不是硬门违规**；仓库既有书面标准优先于本基线，工具已强制的东西不再报。
>
> **单一真源**：12 味坏味道只在**本文件**定义；`cap-code-review/SKILL.md` 只放一行指针，不复述。
>
> **与 severity 正交**：坏味道描述「**是什么类型的问题**」，severity 描述「**有多严重**」。同一个坏味道因影响面不同可标不同严重度（例如同样是「取数长链」，低风险可判最轻一档，跨网络多跳可判较重一档）。severity 枚举与定级判据**只在** `SKILL.md` / `references/severity.md` 定义，**本文件不重复定义 severity 枚举**。

## 用法

1. 对 diff 逐处过一遍 12 味，命中就记「位置 + 味名 + 识别信号」。
2. 再回 `references/severity.md` 按**影响**（正确性 / 安全 / 测试 / 契约 / 可维护性）定严重度。
3. 只标真实命中；**不为凑数硬套**（见文末负路径样例）。

## 12 味基线（识别信号 → 为何有害 → 建议处置）

### 1. 重复片段（同形逻辑多处）
- **识别信号**：同一段逻辑形状在多个 hunk / 多个文件里几乎逐行重复（改一处忘另一处的伏笔）。
- **为何有害**：一份知识散成多份，后续改规则要同步多处，漏改即漂移。
- **建议处置**：把共享形状抽成一个具名单元，两处都调用它；若只是三行样板巧合，宁可保留重复，别硬抽。

### 2. 超长函数（函数过长）
- **识别信号**：一个函数要滚动好几屏、能列出多个抽象层次混在一起、需要靠注释分「第一段 / 第二段」。
- **为何有害**：职责不清、难以单测、复用只能整块复制。
- **建议处置**：按「做一件事」拆成小步，用提取函数把各层意图命名出来；拆出的每一步都能独立读懂。

### 3. 臃肿类（类过大）
- **识别信号**：一个类字段 / 方法成堆，来自多个不同关注点，改动常只涉及其中一簇。
- **为何有害**：上帝类难测、易并发冲撞、牵一发动多处。
- **建议处置**：按变化原因拆分成内聚的小类，用组合代替堆叠。

### 4. 参数成串（长参数列表）
- **识别信号**：同一组参数反复出现、位置相邻含义相近、调用方要按顺序记一长串。
- **为何有害**：易传错序、新增一个参数就改所有调用点。
- **建议处置**：把常结伴的参数收成一个具名类型 / 结构体，作为整体传递。

### 5. 一处多因（发散式变化）
- **识别信号**：同一个文件 / 模块因为好几件互不相关的事被反复修改（不同需求都要动它）。
- **为何有害**：多个变化方向挤在一起，任何一处改动都可能波及其他关注点。
- **建议处置**：把不同变化原因拆到不同模块，让每个模块「只为一个原因而变」。

### 6. 牵一发动全身（霰弹式修改）
- **识别信号**：一个逻辑上的小改动，被迫在 diff 里散落地改很多文件 / 很多处。
- **为何有害**：本该内聚的知识被打散，漏一处就埋 bug，评审也难全 view。
- **建议处置**：把「总是一起改」的东西聚到一个模块，改动收敛到一处。

### 7. 越界访问（依恋情结）
- **识别信号**：一个方法大半时间在伸手掏另一个对象的数据 / 调它的 getter，而不是用自己或近邻的数据。
- **为何有害**：行为放错了家，数据与操作它的逻辑分离，耦合变高。
- **建议处置**：把这段方法搬到它所依恋的那个对象上，或让那个对象自己提供所需行为。

### 8. 结伴字段（数据泥团）
- **识别信号**：同几个字段 / 参数总是成组出现、一起传、一起判空，像一个还没出生的类型。
- **为何有害**：概念没有名字，校验与传递逻辑到处复制。
- **建议处置**：把这组结伴数据提升为一个显式小类型，并把它自己的约束放进去。

### 9. 裸类型顶替（基本类型偏执）
- **识别信号**：用字符串 / 整数 / 布尔去代表一个本该有语义的领域概念（如用 string 当金额、用 int 当状态、用 flag 组合）。
- **为何有害**：单位、取值域、非法组合全靠调用方记，错误在运行时才暴露。
- **建议处置**：给该概念一个小而专的类型，把合法性与单位收进类型里。

### 10. 半吊子字段（临时字段）
- **识别信号**：某字段只在个别方法 / 个别分支里才被设置和使用，其余时间为空。
- **为何有害**：对象状态不完整，读字段前要先猜「这时它有没有值」，易空指针 / 逻辑分支。
- **建议处置**：把「只在某场景用」的数据收敛进该场景专属的对象 / 参数，别挂在长期存活的对象上。

### 11. 取数长链（消息链）
- **识别信号**：`a.b().c().d()` 这种一路点下去的取数导航，调用方被迫认识整条对象图。
- **为何有害**：结构一变全链断，调用方与深层实现强耦合。
- **建议处置**：在链的起点对象上藏一个方法，把这条漫游收进去，对外只暴露一个稳定入口。

### 12. 空壳转手（中间人）
- **识别信号**：一个类 / 函数大部分方法只是原样转发给另一个对象，自己几乎没逻辑。
- **为何有害**：多一层无价值的间接，读代码多跳一层、维护多一处。
- **建议处置**：删掉中间人，让调用方直接找真正的目标；只有当它确实附加了价值（校验 / 缓存 / 边界）才保留。

## 样例 A：能标出 ≥1 处坏味道的评审样例 diff（应对 AC3）

```diff
-function charge(userId, amount, currency, cardToken, saveCard, sendReceipt) {
-  const user = db.users.findById(userId);
-  return gateway.charge(cardToken, amount, currency);
-}
+function charge(user, order, opts) {
+  const raw = db.users.findById(user.id).profile.wallet.defaultCard.token;
+  return gateway.charge(raw, order.amount, order.currency, opts.saveCard, opts.sendReceipt);
+}
```
- **命中 · 第 11 味「取数长链」**：`db.users.findById(...).profile.wallet.defaultCard.token` 一路点到底，调用方被迫认识整条对象图（识别信号命中）→ 建议在 user/repo 上藏一个 `defaultCardToken()` 入口。
- **命中 · 第 9 味「裸类型顶替」倾向**：把 `amount` + `currency` 两个裸值分别传，金额概念没有自带单位 → 建议收成一个金额小类型。
- **定级**：按 `references/severity.md` 结合影响面定（若这是个支付扣款路径，链断了会扣错卡，可判较重；若只是展示路径，多为可维护性小问题）。

## 样例 B：clean diff，套用基线后不硬报（负路径，应对 AC4）

```diff
+function formatDisplayName(user) {
+  const trimmed = user.name.trim();
+  return trimmed.length > 0 ? trimmed : user.email;
+}
```
- 这段是单一职责的小函数、命名自解释、参数是一个有语义的 `user`、无重复、无长链。
- **结论：不命中任何一味**。评审应如实写「未发现坏味道」，或最多对「`email` 作兜底是否合适」给一条最轻的可选建议并注明可接受。**不得为了显得在干活而硬套某味刷量**——这正是本基线要求 judgement call 而非机械套用的原因。

## 边界说明
- 测试代码里的「测试反模式」（如为求绿删断言）归 `review-checklist.md` 第 3 维 / `cap-testing-strategy`，不在本清单重复。
- severity 枚举与定级判据看 `references/severity.md`；六维评审清单看 `references/review-checklist.md`；覆盖率账本看 `references/coverage.md`。本文件只管「坏味道这一发现类型」。

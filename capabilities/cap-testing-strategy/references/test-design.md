## 1. 测试金字塔（默认配比倾向，非教条）

```
        /\        e2e       少量：关键用户旅程、跨系统契约、不能靠下层证明的整体行为
       /  \       integration 适中：组件协作、DB/HTTP 契约、序列化、事务边界
      /____\      unit        大量：纯逻辑、边界、分支、错误处理（快、稳、定位准）
```

选层级的**决策表**：

| 问题特征 | 首选层级 | 理由 |
|---|---|---|
| 纯函数/纯逻辑/算法、分支多 | unit | 快、可精确断言、易证伪 |
| 跨模块协作、DB 读写、序列化、HTTP 契约 | integration | unit 证明不了接缝 |
| 端到端用户旅程、跨进程/外部系统 | e2e（少量） | 昂贵易 flaky，只兜关键流程 |
| 安全约束（防枚举/授权/隔离） | unit/integration + 负路径 | 见 `cap-security-baseline`，用桩/计数 |
| 并发/时序 | 专门并发测试 + 确定性同步点 | 不用 sleep 撞运气 |

> 反模式：把所有东西塞 e2e（慢且 flaky）；或所有东西都 unit（证明不了接缝）。

## 2. 风险驱动覆盖（把力气花在刀刃上）

| 风险档 | 典型区域 | 覆盖要求 |
|---|---|---|
| 高 | 支付/计费、鉴权/权限、数据变更/删除、隐私、破坏性操作 | 主路径 + **完整负路径** + 边界 + 错误处理；高风险分支尽量 100% |
| 中 | 业务规则、状态机、集成契约 | 主路径 + 关键负路径 + 主要边界 |
| 低 | 展示文案、纯 UI 样式、日志 | 冒烟/关键点即可，不堆用例 |

> 覆盖不是「行覆盖%」自嗨：**风险高的分支必须既有正例又有反例**；覆盖率是副产品，不是目标。
>
> **高风险 AC：要么有对应测试，要么在下面的「覆盖排除登记表」逐条写明具体理由。空白/缺省不算覆盖。**

### 2.1 覆盖排除登记表（显式登记，不得默认忽略）

若某个高风险行为**暂不写测试**，必须在登记表里逐行写明，随测试计划一起进入门禁报告：

- **被排除的行为/AC**：具体到哪条 AC、哪个行为。
- **具体理由**：为什么当前无法给出确定性测试（如缺少注入基建、需真实外部系统），不得写「以后再说」「风险低」这类空泛话。
- **残余风险与缓解/监控**：排除后靠什么兜底（日志告警、人工压测、监控、上线灰度）。
- **复核期限**：什么时候必须回来补测。

| 被排除行为/AC | 具体理由 | 残余风险与缓解 | 复核期限 |
|---|---|---|---|
| （示例）AC-7 并发竞态 | 缺真并发注入基建，单测无法确定复现 | 残余：竞态偶发；缓解：加日志告警 + 人工压测 | 下个迭代 |

> 反模式：用空白、缺省或「暂时不管」当「已覆盖」；登记表只写「风险可接受」而不写具体理由与兜底手段——那就是放水通道。

## 3. 负路径 / 边界矩阵（每类输入都要填）

| 输入 | 缺失 | 临界(下/上) | 越界(下-1/上+1) | 合法两端 | 非法类型/格式 |
|---|---|---|---|---|---|
| 必填字段 | 拒绝 | — | — | 接受 | 拒绝 |
| 数值范围 | 拒绝 | 边界接受 | 拒绝 | 接受 | 拒绝 |
| 字符串长度 | 拒绝 | 边界接受 | 拒绝 | 接受 | 拒绝 |
| 集合/分页 | 默认或拒绝 | 1 / 上限 | 0 / 上限+1 | 接受 | 拒绝 |
| 资源归属 | — | — | 越权 ID 拒绝 | 本主接受 | — |

> 每条负路径都要断言：**拒绝的方式正确**（状态/错误码合适）、**不崩溃**、**不回显敏感内部信息**。

## 4. 集成 / E2E 选型

- **集成**：真正需要验证的接缝（SQL 方言、序列化契约、事务、认证中间件）才写；用测试容器/内存 DB 而非 mock 掉整个依赖（否则等于没测契约）。
- **E2E**：只覆盖「必须端到端才算数」的关键旅程（登录→下单→支付成功），数量控制在少数；不稳定就下沉到 integration。
- **契约测试**：服务间用契约（schema/示例）固定接口，避免 e2e 爆炸。

## 5. AC → 测试追溯表（模板，必填）

```
| AC 编号 | 行为断言（可观察） | 测试名 | 层级 | 负路径? | 状态 |
|---|---|---|---|---|---|
| AC-1 | 分页 size=上限+1 返回 400 | test_page_size_over_max | unit | 是 | pass |
| AC-2 | 跨租户读返回 404 且不泄露存在性 | test_cross_tenant_denied | integration | 是 | pass |
| AC-3 | 下单成功扣减库存 | test_checkout_decrements_stock | integration | 是(库存不足) | pass |
```

要求：每条 AC ≥1 行；无「孤立测试」（无 AC 对应）除非登记原因；负路径列不得全空（高风险 AC 必填）。**高风险 AC 要么有测试、要么在 §2.1 覆盖排除登记表写明具体理由——登记不得为空泛理由。**

## 6. Flake 诊断（不许靠重试掩盖）

1. **复现**：记录失败率与条件（并行/顺序/时间/数据）。
2. **定位根因**：共享可变状态、真实时间/`sleep`、网络、端口、随机、跨测试顺序依赖、异步未 await。
3. **修根因**：注入时钟/固定种子、隔离状态、等待条件而非 sleep、确定性同步点。
4. **禁止**：`retry` 掩盖、无限放大超时、跳过。

## 7. 与证伪性/变异思维衔接

写完测试后做「**若把实现改坏，这条测试会红吗？**」自检；不会 → 换可观察断言。系统化的示范见 `anti-test-count.md` 与 `scripts/falsification_demo.mjs`。

## 8. 强制动作与「什么都不做」缺陷（零动作探针）

有些需求约束的是**必须发生的动作**：写审计日志、扣减库存、发送通知、落库、调用鉴权、释放锁。对这类需求，只验证「做了的时候结果对不对」不够——实现可能**整个跳过该动作**，而常规 happy-path 测试仍可能全绿，于是漏做无人发现。

- **做什么**：为每个强制动作建一条**零动作缺陷探针**——构造一个『跳过该动作』的坏实现（例如把该动作换成空操作 / 直接 `return`），断言对应测试**必须失败**；正确实现下必须通过。
- **怎么判**：坏实现下测试**红**、正确实现下**绿** = 该动作被真正检验；坏实现下仍全绿 = 漏检，必须补断言——通常要断言**可观察副作用**（写入了几条记录 / 库存变化量 / 实际发出的消息 / 锁状态），而不是只断言「返回成功」或「方法被调用」。
- **反模式**：只断言「动作返回成功」而不校验副作用；只用 mock 断言「内部方法被调用」却不在集成层验证真实效果；把「跳过动作」当不可测而登记排除——除非理由具体、兜底明确且经评审。

## 9. 不可测验收标准：识别、上报、受控降级

有些验收标准在当前条件下**无法转成可执行的失败测试**——不是因为「还没来得及写」，而是因为**缺乏客观可断言的结果**（例如「界面要好看」「响应要够快」这类没有阈值的形容词，或依赖无法注入的外部人工环节）。这与 §2.1「覆盖排除登记表」是**不同触发条件**：§2.1 管的是「该测但暂时缺测试」，本节管的是「AC 本身不可测」。两者都要显式登记，但闭环不同。

- **做什么**：
  1. **分类**：逐条把 AC 分成**可测**与**不可测**。判据是「能否写出一个在实现做错时必定变红的客观断言」——写得出=可测；写不出、也给不出客观判据=不可测。
  2. **保留完整清单 + 理由**：不可测项**留在完整 AC 清单里**并逐条写明**具体理由**（为什么没有客观可断言结果），不得删除、隐藏或用「以后再说」搪塞。
  3. **默认 halt**：默认策略是**停机**——不可测标准不自动放行；只有在**显式开启**的受控降级策略下才允许 `skip-and-report`：跳过该条但**如实上报被跳过的条目与数量**，并继续推进**可测子集**。
  4. **可测子集全覆盖**：完成前校验「**每个可测 AC 恰有一个可执行测试/脚手架、无遗漏**」——降级只针对不可测项，不能顺带漏掉可测项。
  5. **全不可测则 halt**：若某范围内**全部 AC 都不可测**，整体 halt，不产出「已覆盖」的假结论。
  6. **降级不得被悄悄篡改**：降级策略一旦选定并记录，在恢复（checkpoint/续跑）时**必须沿用**，不得被静默改回默认或改成更宽松的策略。

- **怎么判**：
  - 对每条被标「不可测」的 AC，问：**把这条理由交给另一位评审者，他能据其独立复核「确实无法客观断言」吗？** 给不出客观判据 → 其实可测，退回重写成可观察断言。
  - 若走了 `skip-and-report`：门禁报告里必须**同时**出现「被跳过条目清单 + 数量 + 理由」，且**可测子集覆盖率满**（每个可测 AC 恰一个测试/脚手架）。缺任一 = 不合格。
  - 恢复后核对：降级策略须与 checkpoint 前记录**一致**；若被改宽又无显式变更说明 = 篡改，判失败。

- **反模式**：
  - 把「不可测」当放水通道：默认就想跳过、不写理由、不登记数量——违反「默认 halt」。
  - 用形容词（「更快」「更友好」）掩盖「没想清楚怎么断言」，把**本可测**的 AC 误标成不可测以逃避测试。
  - 只登记不可测项，却漏掉**可测子集**的覆盖校验（该测的可测项没测）。
  - 在恢复/续跑时**悄悄把降级策略改宽**，事后又声称「一直如此」。

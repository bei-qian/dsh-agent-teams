## 为什么需要统一词汇

设计讨论最常见的失败，是同一个东西被叫成「组件」「服务」「API」「边界」「层」，各说各话，判据也随之漂移。统一几个词，讨论才能落到**可复核**的判断上：接口多宽、深度够不够、seam 该在哪、删了会怎样。**用词一致本身就是这套词汇的价值**，不要随手替换成同义词。

## 七个词汇（自写定义 + 可操作判据）

### 1. Module（模块）
- **定义**：任何「有接口 + 有实现」的东西；**尺度无关**——可以是一个函数、一个类、一个包，也可以是一段横跨多层的切片。
- **可操作判据**：能清楚回答「调用方需要知道什么才能正确使用它」（有接口）；且接口背后有被隐藏的实现体。若一个东西既没有调用方需要遵守的约定、也没有隐藏任何东西，它就不是有意义的模块。

### 2. Interface（接口）
- **定义**：调用方为**正确**使用该模块必须知道的**全部事实**——不只是类型签名，还包括：不变量、调用 / 初始化顺序约束、错误模式与失败语义、必需配置、性能 / 复杂度特征。
- **可操作判据**：一个新调用方**只读接口描述**就能正确调用，无需读实现；反之，凡是「不读实现就会用错」的信息，都算接口的一部分，漏写即接口不完整。

### 3. Depth（深度）
- **定义**：接口上的**杠杆量**——调用方（或测试）每学一单位接口，能撬动多少行为。**深 = 小接口 + 大量行为**；**浅 = 接口复杂度逼近实现复杂度**。
- **可操作判据**：把「调用方必须学的接口面」（方法数 / 参数数 / 需要理解的约定数）与「背后的行为量」并列比较；**接口面变小、行为量变大 = 变深**。

### 4. Seam（接缝）
- **定义**：一个**不必改动该处本身、就能改变行为**的位置；接口就长在 seam 上。seam 放哪，是一个独立于「里面放什么」的设计决策。
- **可操作判据**：问自己「我想在不碰调用方的前提下替换 / 变更实现，该改哪里？」——那个点就是 seam。若为了实现替换必须回头改调用方，说明 seam 放错了地方。

### 5. Adapter（适配器）
- **定义**：在某个 seam 上、满足某个 interface 的**具体物**。它描述的是**角色**（填哪个槽），不是**实质**（里面装什么）：可以「小适配器 + 大实现」（如一个真实数据库仓储），也可以「大适配器 + 小实现」（如一个内存假件）。
- **可操作判据**：看同一个 interface 是否存在 **≥2 个可互换实现**：有两个真实实现 = 真 seam，值得适配器；只有一个实现 = 假想 seam，先别引入。

### 6. Leverage（杠杆，调用方视角）
- **定义**：调用方从深度得到的好处——**一份实现，回报在 N 个调用点 + M 个测试上**。
- **可操作判据**：数同一个实现被多少调用点 / 测试复用；复用点越多，杠杆越大，越值得让它变深。

### 7. Locality（局部性，维护者视角）
- **定义**：维护者从深度得到的好处——改动、缺陷、知识、验证**集中在一处**，而不是散落到各调用方。修一次，处处生效。
- **可操作判据**：修一个 bug / 改一处逻辑，需要动几个文件、几处调用点？越少 = 局部性越好；若每次改动都要同步 N 个调用方，说明深度没落在接口上。

> **词间关系（速记）**：一个 **Module** 恰好有**一个 Interface**（对调用方与测试呈现的那个面）；**Depth** 是 Module 相对其 Interface 的性质；**Seam** 是 Interface 所在的位置；**Adapter** 坐在 Seam 上满足 Interface；**Depth** 给调用方产生 **Leverage**、给维护者产生 **Locality**。

## 深 vs 浅（示意）

```
深模块 = 小接口 + 大量实现（想要的）      浅模块 = 大接口 + 薄实现（避免）
┌───────────────────┐                     ┌─────────────────────────────┐
│  小接口（少方法）  │                     │  大接口（多方法、多参数）    │
├───────────────────┤                     ├─────────────────────────────┤
│                   │                     │  薄实现（大多是直传/转发）   │
│  深实现（藏复杂度）│                     └─────────────────────────────┘
│                   │
└───────────────────┘
```

## Deletion Test（删除测试，可执行步骤）

「删掉这个模块，它的复杂度是**消失了**，还是**搬到调用方去了**？」这是判断「它到底有没有在承担真实深度」的核心可执行检验。

**步骤：**
1. **假想删除**该模块及其接口，但**保留所有调用方**。
2. 逐个调用方问：原来由这个模块提供的那部分复杂度（逻辑 / 校验 / 边界处理 / 协调），现在**去哪了**？
   - 若**消失**了 → 它很可能只是 **pass-through 的浅层转发**，删掉反而更简单，不该当成深模块保留。
   - 若**重新出现在 N 个调用方**（每个调用方都得自己重写同样的逻辑 / 校验 / 兜底）→ 它在**承担真实深度**，值得保留 / 深化。
3. **结算成可复核清单**：「删后复杂度搬到哪些调用方、每处搬了多少」。**N ≥ 2 且每处都需要真实逻辑 = 深；N = 0 或只剩直传 / 一行委托 = 浅**。
4. **防伪**：如果复杂度只是「搬成调用方多一行 import / 一行委托」，那说明模块没真正承载深度——别把「多一个转发点」误判为「有深度」。

## Interface = Test Surface（接口即测试面）

- **判据**：调用方与测试**穿过同一个 seam**。测试应当**只经接口**就能覆盖该模块的全部**关键行为**；**模块越深、接口越窄，越应能用少量窄接口测全行为**。
- **反例（形状错的信号）**：要测某个行为，必须绕过接口去碰私有方法 / 大量 mock 内部细节 / 直接读内部状态——说明接口没有覆盖真实行为，或 seam 放错，**深度没落在接口上**。
- **配套的好接口让测试自然**：① **接受依赖，而不是自己 new**（便于注入假实现，测试天然）；② **返回结果，而不是产生副作用**（便于断言）；③ **接口面小**（方法少、参数少 = 测试桩少、setup 简单）。

## 「是否该深化」的可复核判据（决策清单）

逐条勾，**任一关键项不满足就别深化**（回到 KISS / YAGNI / 先做能跑的最简实现）：

- [ ] **deletion test 显示删掉后复杂度会在 ≥ 2 个调用方重现**（确认真实深度存在）。
- [ ] **接口确实偏宽 / 偏杂**，存在可收敛的多余方法 / 参数 / 需要调用方自理的重复逻辑。
- [ ] **存在 ≥ 2 个真实变化点跨过 seam**（真 seam → 值得引入 adapter / 深化）；若只有一个实现 → 先别抽。
- [ ] **深化后测试能只经接口覆盖全部关键行为**（interface = test surface 成立）。

→ 全部满足：这是**健康深化**（把复杂度藏到窄接口后，Leverage / Locality 上升）。
→ 有任一不满足：**保持最简单能跑的实现**，别为套词汇而加层。

## 反例 / 何时不需要深化（避免过度设计与误用）

- **故意做浅的薄适配 / 声明式接线**：例如只做「re-export / mount」的薄 shim——删掉它复杂度**不会消失**，而是接线塌回共享层、丢掉每行身份（per-row identity）。这类薄模块**接受浅**，别硬加深。
- **领域简单、只有一个调用方**：为「以后可能」而加深 = 过渡设计（YAGNI）。
- **单一实现、无真实变化点**：不要造「假想 seam」和「满配 adapter」。
- **不要把「深模块」误用为「黑箱」**：深度是「**窄接口 + 丰富的、可被接口完整测到的行为**」，不是「把复杂度藏起来让谁都看不懂 / 测不到」。若接口无法表达关键不变量、测试只能靠猜 → 那不是深，是**坏封装**。

## 应用样例：对现有模块 `scripts/squad_validate.mjs` 的「是否该深化」判断（可复核）

- **Module**：`scripts/squad_validate.mjs`（零依赖票据校验器）。
- **Interface**：一个 CLI——可选 `[dir]` 参数（默认 `./bmad-output`）+ **退出码**（0 通过 / 1 有硬错误）+ 两行状态 / 警告输出。调用方要学的东西极少（一条命令 + 看退出码）。
- **Implementation**：约 100 行契约检查——`index.md` 表列顺序、`type` / `status` 枚举、每个 `file` 存在性、重复 id、`initiative.md` 存在与标题、`done` story 缺「验收标准 / 实现 / 验证」的警告等。

**Deletion test（若删掉该脚本，复杂度搬到哪些调用方，可复核）**：

| 调用方（可复核） | 删掉后它得自己补什么 |
|---|---|
| `playbooks/bmad-squad-protocol/SKILL.md` 阶段门（每个成员 / Lead 每次收尾都跑） | 每个成员手工核对 index 表列 / 状态枚举 / 文件存在性 / 重复 id（重复劳动散到全体） |
| `scripts/verify.mjs`（第 9 段，对 `examples/bmad-output` 冒烟跑） | verify 需内联一份同等契约检查 |
| `scripts/check_gate_cmd.mjs`（钉住阶段门命令：存在 + `--help` 退出 0 + 协议里引用路径不变） | 门禁命令失去被钉住的对象，路径漂移无人拦 |
| `package.json`（`validate` / `validate:sample`）+ `.github/workflows/verify.yml`（经 verify.mjs 间接覆盖） | npm 脚本与 CI 失去可调用入口 / 覆盖对象 |

- **Deletion test 结论**：删掉后「固定目录契约 + index 表校验 + 枚举 / 存在性 / 重复 id 检查」**不会消失，而是重现在上述 ≥ 4 个调用方**（全体成员手工纪律 + verify 内联 + CI + npm scripts）→ 它在承担**真实深度**，值得保留。
- **深化建议（理由）**：**已足够深，不建议再拆**。接口已是「单命令 + 退出码 + 状态行」的窄面；若把内部各项检查（如「index 列校验」「done 节警告」）拆成**公开子命令**，等于把实现细节暴露到接口 → 接口变宽 → 反而变浅。若确有变化需求，也只在**内部 seam**（私有函数）重构，**保持外部 CLI 接口不变**（interface = 测试面：测试只经 `node squad_validate.mjs <dir>` + 退出码就能验证行为）。
- **一句话可复核判断**：`squad_validate.mjs` 是**深模块**，**保留且不扩接口**；不应为了「套深模块词汇」而把内部检查拆成多个对外脚本。

# 架构（Athena）

## 何时用
需要定技术选型、模块边界、接口/数据流，让分开构建的部分保持一致时。

## 先读
- `bmad-output/initiative.md`、`bmad-output/prd.md`、`bmad-output/design.md`
- 现有代码/文档（先复用既有模式，不无谓造新机器）
- 深模块词汇 / deletion test 见 `reference/deep-modules.md`（判断模块深度 / seam 时按需深读，此处不复述）

## 步骤
1. 列出关键决策点（技术选型、边界、接口、数据流）。
2. 每个决策给背景/选项/选择/后果（ADR 形式，可多条）。
3. 覆盖边界情况、失败模式、测试与验收的架构含义。
4. 落盘 `bmad-output/architecture.md`。

## 安全与非功能风险分析（认证 / 授权 / 密钥 / 敏感数据）

当系统涉及认证、授权、密钥或凭据管理、密码、或任何敏感数据时，架构必须在常规边界与失败模式之外，显式产出一份**安全与风险分析**，作为 ADR 的一部分，并满足：

- **产出要求**：明确信任边界、认证 / 授权模型、密钥与凭据管理、密码学原语、账号枚举面、时序 / 侧信道等非功能风险的**架构结论**（不在此逐条展开技术约束清单）。
- **每条安全决策落成可测试的约束**：标注对应验收方式（供票据 AC 与测试用例直接引用）；无法自动测试的残余风险须显式记录、说明理由并给出缓解或监控手段。
- **威胁建模深度 / 具体技术约束归能力**：威胁建模方法（STRIDE）、认证与输入校验细节、供应链检查等**深度内容见 `cap-security-baseline`**（`capabilities/cap-security-baseline/references/*`）；本技能只负责「架构需产出安全分析」这一骨架与产出要求，不复制逐条约束。

## 模式选型（交叉引用）
后端设计模式**怎么选、要不要上**属架构决策——**归本技能（Athena）**：回答是否/为何选某个模式、边界与取舍；**落地实现归 Hephaestus**（`bmad-build`）。决策表与实现规则**只在 `bmad-build` 维护一处**，本技能**不复制正文**，只给入口：
- 选型与硬规则：`bmad-build/SKILL.md` 的〈后端设计规范（取自 java-design-patterns 精选）〉节及其「问题→模式→参照路径」决策表。
- 按需深读：`bmad-build/reference/`——先用一页摘要索引 `reference/README.md` 速查，再读 `<类别>/<pattern>.md`。

## 术语与 ADR 纪律（单一真源）

> 本节是「领域术语 / GLOSSARY」与「ADR 三条触发」的**唯一正文出处**。`bmad-research` / `bmad-prd` 只用一行指针引用本节，不复制规则，避免三处各写一套。

### 术语表（GLOSSARY）纪律

- **主动建 / 磨术语**：在设计讨论里主动建设、打磨领域术语，把口头模糊的说法固化成可复用的规范术语。
- **术语消歧（一句话规则）**：**一个术语只允许一个含义**；遇到模糊或过载术语（一词多义 / 多词一义）先当场消歧、定一个规范术语，再往下走。
- **挑战口径**：术语与既有定义冲突、或「口头说法 vs 代码行为」矛盾时，立即指出并要求二选一，不带着歧义继续设计。
- **落点（产物 / 指针）**：定案的术语条目写到 `bmad-output/` 下的**产物或指针**（如 `bmad-output/research/glossary.md`，或 PRD / architecture 的「术语」节）；只在第一个术语被定案时按需创建，不提前造空表。
- **非票据真相（硬约束）**：**术语表非票据真相、不新增第二真相源**。票据状态 / 依赖 / 范围**仍只在 `index.md` / `initiative.md`**；术语表**不得承载实现细节、不得记录票据状态字段**，且 **`index.md` 不得出现指向 glossary 的票行**。

### ADR 三条触发（三条同时成立才开 ADR）

只有下面三条**同时成立**才开一条 ADR；缺任一条就**不开**，避免 ADR 泛滥：

1. **难回退**：日后改主意的代价显著，不是随手可改。
2. **脱离上下文费解**：未来的读者会问「当初为什么这么做」。
3. **真权衡**：确实存在可选的替代方案，且是为具体理由选了其一。

反例（缺任一条即**不建** ADR）：
- **可逆**的小改动、随手能改回 → 不建。
- **一眼自解释**、未来读者不会困惑 → 不建。
- **没有替代方案、没有取舍**（被迫如此）→ 不建。

ADR 的书写结构沿用本文件〈architecture.md 模板〉的 ADR 小节；本节只回答「**何时该开 ADR**」，不改写模板本身。

## 架构巡检（定期扫架构 → 深化候选清单，不直接改码）

**何时用**：按节奏（如每 N 个 epic 收尾）或 retro 想补「架构健康」视角时，扫描现有模块、找**深化机会**（把浅模块变深模块），产出**候选清单**供研判。**巡检只产出候选，不在巡检里重构 / 改码**。

**步骤**：
1. **定范围（YAGNI 先行）**：优先扫最近反复改动 / 有痛点的模块；Lead 或用户已点名方向就直接用，别全库铺开。先读该区已有的 ADR / 术语，避免重提已被明确否掉的方案。
2. **扫浅模块**：找「接口复杂度逼近实现复杂度」「理解一个概念要在多个小模块间来回跳」「纯为测试抽出的函数、真实 bug 却藏在调用方（locality 差）」「耦合跨 seam 泄漏」「难用现有接口测」这类摩擦。
3. **用 deletion test 判定**：对可疑模块套 deletion test——删掉它复杂度是**消失**（浅转发）还是**搬到 ≥2 个调用方重现**（真实深度）。**深模块词汇、deletion test 的可执行步骤、interface=测试面、以及「是否该深化」的勾选判据，单一真源在 `reference/deep-modules.md`（源自 story-041），本节只引用、不复述**。
4. **产出候选清单（每项可复核）**：`现状`（哪个模块 / 什么摩擦）→ `before/after 理由`（当前浅在哪、深化后如何变深，用深模块词汇表述）→ `预期收益`（leverage / locality / 可测性）→ `风险 / blast radius`（影响哪些调用方 / 测试）→ `推荐强度`（强 / 值得探索 / 存疑）。
5. **只产出清单，不改码**：巡检的产物**仅是候选清单**；每条候选**转 ticket**（story / task，由 Themis 在 `index.md` 建行）或作为 retro 改进项，交正常实现流程落地。**巡检本身不产生任何源码 diff**（`git diff` 只应出现 playbook 正文与本票据的候选样例）。

**何时不该深化 / 不该立项（避免为巡检而巡检）**：
- 「何时不需要深化」的判据（薄适配 / 声明式接线 / 单一调用方 / 单一实现无变化点）**单一真源见 `reference/deep-modules.md`「反例 / 何时不需要深化」，本节不复述**。
- **预期收益 < 改动风险 / blast radius**：记为观察项，不立项。
- 只是「一眼看不懂」而非「改起来痛」：先补文档 / 命名，不上升为深化。

**与 retro 的边界**：retro 复盘**运行过程**（这次怎么跑、下次怎么更省更准）；架构巡检看**架构健康**（结构该不该深化）。巡检清单可作为 retro 的一类改进来源，转 ticket 时复用 retro 的「改进项→转 ticket」闭环（见 `bmad-retro`），**不另造第二套流程**。

## 一次性逻辑 / 状态原型（指针）

设计里遇到**状态机 / 并发 / 数据流 / 不变量**这类**逻辑 / 状态**问题、纸面推演不够时，可用**一次性原型**（throwaway 脚本 / 伪代码 / 状态表，脱离生产代码）快速验证，再把**结论**沉淀为主源 / 指针。

- **纪律正文（单一真源）见 `bmad-ux/SKILL.md`〈一次性逻辑 / 状态原型〉**：何时用、throwaway 与清理、结论留存为 `bmad-output/` 产物 / 指针、与 UI 原型模板去重、何时不该做原型——此处不复述。
- **架构侧落点**：与架构相关的原型结论可直接写进 `bmad-output/architecture.md` 的对应小节（或 `bmad-output/research/proto-<问题>.md` 指针），供 ADR / 模块边界引用；结论是证据 / 指针，**非票据真相**。

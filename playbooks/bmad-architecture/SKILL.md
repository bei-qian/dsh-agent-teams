# 架构（Winston）

## 何时用
需要定技术选型、模块边界、接口/数据流，让分开构建的部分保持一致时。

## 先读
- `bmad-output/initiative.md`、`bmad-output/prd.md`、`bmad-output/design.md`
- 现有代码/文档（先复用既有模式，不无谓造新机器）

## 步骤
1. 列出关键决策点（技术选型、边界、接口、数据流）。
2. 每个决策给背景/选项/选择/后果（ADR 形式，可多条）。
3. 覆盖边界情况、失败模式、测试与验收的架构含义。
4. 落盘 `bmad-output/architecture.md`。

## 安全与非功能风险分析（认证 / 授权 / 密钥 / 敏感数据）

当系统涉及认证、授权、密钥或凭据管理、密码、或任何敏感数据时，架构必须在常规边界与失败模式之外，显式产出一份安全与风险分析，至少覆盖：

- **信任边界**：明确哪些组件、通道与输入不被信任；信任在哪一层建立、在哪一层校验，越界如何处理。
- **认证 / 授权模型**：谁以何种凭据证明身份、能访问什么；未认证 / 越权 / 会话失效时如何失败且不泄露信息。
- **密钥与凭据管理**：密钥 / secret 的来源与注入方式、强度要求、缺失或过弱时的失败行为（如 fail-fast）、轮换与「绝不记录」的约束。
- **密码学原语**：哈希 / KDF、签名、消息比较所用的原语与参数及其安全性理由；说明为何不自制密码学，以及参数升级 / 迁移路径。
- **账号枚举面**：注册、登录、找回等响应在状态码、文案、时序上的可区分性；要求对「账号存在 / 不存在」不可区分。
- **时序与侧信道等非功能风险**：冷启动与稳态的算力差异、各失败分支间的可观测差异、日志 / 异常 / 错误信息的泄露面、资源耗尽与限流。

每条安全决策都要落成**可测试的约束**（可被确定性断言，而非仅凭墙钟耗时或人工判断），并在写 ADR 时标注其对应的验收方式，供票据 AC 与测试用例直接引用；无法自动测试的残余风险须显式记录、说明理由并给出缓解或监控手段。

## 模式选型（交叉引用）
后端设计模式**怎么选、要不要上**属架构决策——**归本技能（Winston）**：回答是否/为何选某个模式、边界与取舍；**落地实现归 Amelia**（`bmad-build`）。决策表与实现规则**只在 `bmad-build` 维护一处**，本技能**不复制正文**，只给入口：
- 选型与硬规则：`bmad-build/SKILL.md` 的〈后端设计规范（取自 java-design-patterns 精选）〉节及其「问题→模式→参照路径」决策表。
- 按需深读：`bmad-build/reference/`——先用一页摘要索引 `reference/README.md` 速查，再读 `<类别>/<pattern>.md`。
